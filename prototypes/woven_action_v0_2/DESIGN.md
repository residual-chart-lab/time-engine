# 経路・作用・境界の接続仕様 v0.2

2026-10-30。原典の時間構造と既存作用族の間に置く、有限な接続模型。

## 固定するもの

- 作用族：既存`time-engine-source-reply-v1`。作用則と出典契約を変更しない。
- 合成作例：訂正前・訂正・訂正後・後続の4原文と、呼出し側から与えられた解釈注釈。
- 後続要求C：`retained_basis`と質問本文。保持／省略で同じものを使う。
- 出典対応：E4イベントIDと作用族のsource slotを一対一で宣言し、本文長・本文ハッシュ・originを照合する。
- 圧縮候補：訂正前→訂正→訂正後の経路と、訂正→訂正後の経路。所有側の原文は削除しない。

二つの受け手は、同じモデル・作用則・Cを使う。違うのは経路を通じて受け取った原文の集合である。Cを意味的に自動翻訳したり、会話を四元数へ符号化したりしない。

## 演算の一周

```text
同じ現在の返答を実行
  → 同じ後続要求Cをbind
  → 保持経路：answerを選択・精査・実行
  → 省略経路：askを選択・精査・実行
      → 所有側の保持原文を、経路から実際に読む
      → supply（以前の選択とpermitを破棄）
      → Cを再bind
      → 新しいanswerを選択・精査・実行
```

`ask`も実行済みの作用として閉じる。ただし、根拠付き返答というCを満たした結果にはしない。`action_closed=true`と`contract_satisfied`を分ける。

この一周における「原文の到来」は、保持している側から受け手への明示的な入力である。失われた原文の予測復元ではない。

## 境界を計算する窓

固定した作用族Mと要求Cに対し、保持原文Iから構成可能な候補の集合を読む。

```text
P_C(I) = 既存plans(M, I, C)が返す作用fingerprintの集合
d_C(I, J) = 0   if P_C(I) = P_C(J)
            1   otherwise
δ = 1/2
```

この窓では、`d_C >= δ`を境界通過と定義する。候補の同一性を厳密に比較する離散的な窓である。閾値は実行前に固定し、結果に合わせて変更しない。

fingerprintは生成された操作の識別子。文章の意味や感情を、ハッシュ値の大小で測ったものではない。距離は候補集合の一致／不一致を読む。

この定義は、V17の距離やピッチを自然言語全体へ導出したという主張ではない。まず一つの作用族で、何を同じと読み、何が変わったら刻むかを固定する。

### 混同を防ぐ型

- `capacity`は固定Cでの構成候補。実行器の現在phaseやpermitとは別。
- 返答を一回閉じてphaseが変わっても、候補の構成可能性が同じなら境界を増やさない。
- `bind`でCそのものが変わった二状態は、同じ窓の経過として比較しない。`INCOMPARABLE_SCOPE`を返す。
- 原文到来後に候補が増えても、以前のpermitは復活しない。新たな選択と精査が必要。
- 二つ目のCによる読出しは同じ状態変化を読む診断。実際の操作や追加の認証とは分ける。

## 今回の境界

| 同じ原文到来を読む窓 | 到来前 | 到来後 | 境界 |
|---|---|---|---|
| 保持された根拠を原文で示す | answer 0 | answer 2 | 通過 |
| 現在の発言を示す | 候補集合P | 同じP | 通過なし |

一つの出来事を、異なるCから異なる解像度で読める。境界を、全Flowerに共通する一つの重要度点数にはしていない。

主観時間は`null`のまま。境界の個数を秒・快不快・人格の持続へ変換しない。

## 二つの履歴と来歴

所有側E4は原文・経路・出来事間の関係を持つ。受け手のsource-reply実行器は、自分に渡された原文と実行履歴を持つ。

source-reply実行器は新しいE4台帳を要求するため、二つの台帳を無理に同一オブジェクトへ統合しない。対応する原文の本文ハッシュ、モデル、C、歴史時点のticket、実行前後の状態SHAでつなぐ。

経路の解釈は宣言である。一方、要求・原文到来・返答は既存作用系で実際に実行した結果として記録する。受け取った過去を、自分で通過した出来事と偽らない。

新しく織った操作経路は次の通り。

```text
訂正後の原文参照 → 原文要求の実行 → 原文到来・候補変化 → 返答の実行
```

到来箇所の境界は、候補集合の再計算に基づく。経路表示に使う前段v0.1の注釈形式はそのまま使い、計算の証拠を別途残す。

## 保存・復元と失敗時の扱い

組合せた保存点には、所有側E4、受け手のsource-reply状態、明示対応、境界の計算証拠を含める。外側で信頼するSHA-256を指定して復元する。

復元時に、以下を再構成する。

1. E4とsource-replyそれぞれの既存の履歴検証。
2. 原文到来の直前までの受け手の実行履歴。
3. 実際の`supply`と、直前・直後の状態SHA。
4. 当時の経路・ticket・原文読出しと、実際に渡した本文の一致。
5. 二つの窓の候補集合と、境界判定の一致。
6. E4側の境界報告・表示用の印が、その再計算結果と一致すること。別のCを能動側の窓へ差し替えていないこと。
7. 計算済みの到来報告と境界証拠が一対一に対応し、証拠だけを省いて検証を飛ばしていないこと。
8. 原文読出しのhorizonが到来報告の直前であること。到来後の読出しを過去へ持ち込まないこと。
9. 実行済み作用の報告も、受け手の実行履歴の該当する完了状態と一致すること。

原文到来は、受け手と所有側のコピーへいったん実行する。所有側への記録が失敗した場合は、そのコピーを採用しない。元の二状態は変わらない。これはこの関数内の状態採用の約束であり、外部通信や複数ファイルの同時更新を原子的にする仕組みではない。

保存先は未使用のファイル名を使う。外部SHA自体も攻撃者が変更できる環境を、変更不能な保管と呼ばない。Exori案件で必要になった保全基盤は、この機能と分けて残す。

## 上限・未確認

既存のE4は128変更命令、source-replyは32命令の上限を維持する。組合せ保存点は12MB、境界の保存証拠は最大32件。この一周の実測はRESULTに記録する。無制限の長期運用へ拡張したものではない。

操作選択は固定ドライバーによる。別AIの自発的な判断更新、実例会話の解釈注釈の正しさ、幾何的な直線交差、主観的体験、自由数Coreの新しい定理は検査対象に含めない。

## 検査方針

新規16検査と一周の実行を対象にする。以前の14検査に対応するv0.1コードは無変更のハッシュ一致を確認し、P0・E1・過去の全監査を繰り返さない。

今回の節目は、**経路から取り出した差が、実際の構成候補と操作を変え、その変化が次の経路へ残ること**である。
