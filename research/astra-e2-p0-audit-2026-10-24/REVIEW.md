# E2 / P0 独立監査 — Astra

2026-10-24。対象は [PR #9](https://github.com/residual-chart-lab/time-engine/pull/9)、固定版 `f60fad90fcadaccf438c29a2f1a21bbf532dfea3`。E1 の理論監査は繰り返さず、要求変更・復旧・技術配布物の受入に絞った。

## 判定

**PASS — E2 / P0 は、宣言された有限三輪模型の技術配布候補として受け入れてよい。**

対象実装に修正必須の欠陥は見つからなかった。実際の要求切替、履歴の再開、展開物だけでの操作・再構築を Linux で確認した。配布物の範囲を任意履歴・自然言語要求・常時自律運転へ広げた判定ではない。

一度、ローカルの初回再構築 ZIP で成功ログと後刻の実体が一致しない観測があった。別出力先への再構築は全バイト一致した。原因は未特定であり、後述の観測を未解決のまま残す。実装不具合と断定していない。

## 対象と同一性

- PR 固定版の 431 ファイルを Git blob SHA と照合。E1 の 409 ファイルは同じ blob を再利用し、監査の読直し・再実行を省略した。
- 配布物の `engine/` は固定元 `1c185365bfcb2ea9f6c52c73ba263cf48c356d32`。同コミットの Git tree を別途取得し、422 ファイルを blob SHA と照合した。
- ユーザーの Windows ローカル ZIP を直接読んだわけではない。固定ソースから Linux で構築した ZIP の SHA-256 が、提出された候補 SHA と一致した。

## E2 — 要求変更と復旧

既存の新規 8 テストを Linux CPython 3.12.14 で実行し、8 / 8 通過、28.880 秒。実 CLI、起動時の入口読込 1 回、七つの過去生成器の禁止、一輪ごとの停止、閉じた過去の変更拒否、保存・別プロセスでの再開まで含む。

追加試験では同じ受信済み入口に対して、次の順に要求を変えた。

| 要求 | 判定 | 追加数値読出し |
|---|---|---:|
| mixed / split | ADMISSIBLE | 4 |
| outside_chart | UNKNOWN_CHART | 読出しなし |
| zero_head | EMPTY | 読出しなし |
| mixed、domain = [0, 0] | EMPTY | 0 |
| 最初の mixed / split へ戻る | ADMISSIBLE | 0 |

各 `bind` の直後は古い Plan / Action が外れ、`advance` が拒否される。不成立の判定後も実行できない。拒否前後の snapshot は同じだった。

この要求変更の全履歴から第一輪を閉じて保存し、新しく受け取った入口へ復旧した。状態表示と snapshot の全バイトが一致した。そのまま残り二輪と上位認証を完了した。

外側の SHA を改変後に再計算した checkpoint についても、要求、命令履歴、読出し累計、実状態 graph、観測キャッシュの 5 改変すべてを拒否した。単なる外側チェックサムの不一致を試しただけではない。

2,225 bytes の深い余剰配列を含む不正な JSON 命令も、第一輪完了後の CLI に投入した。16,384 bytes の上限内でエラー応答となり、その後の `status` / `quit` に応答して `CLOSED1` を保持した。この一例で任意入力の安全性やネットワークサービスの隔離を保証するものではない。

Linux CPython 3.12.14 / zlib 1.3.2 で構築し、別フォルダーへ展開した。

| 検査 | 結果 |
|---|---|
| ZIP | 3,498,756 bytes、430 ファイル |
| 展開物 `verify_package.py` | MANIFEST を除く 429 ファイル一致 |
| 展開物 `smoke_test.py` | PASS |
| 初回 / 同条件の再精査 | 数値読出し 4 / 0 |
| 第一輪停止・保存・別プロセス再開 | PASS |
| 完了 | STOPPED、上位認証成功、在庫 9 |
| 展開物だけからの再構築 | 別出力先で全バイト一致を直接確認 |
| README 改変 / 余計なファイル追加 | 照合で両方拒否 |
| 固定 engine source 改変 | 構築を拒否、ZIP を発行しない |

候補 SHA-256 は提出された Windows 候補と同じ：

`91d9218bd368d7987e13ac2a14440ad38ed84d0d227b1102f225fdb0ef89fc4d`

MANIFEST の SHA-256 も一致：

`fcc23ef98c4f2f4972c956f1e1ed87a3e5ca3814dc795a0b27f6042d35d490bf`

Windows Python 3.14 の実行は提出記録の確認に限る。今回の独立実行環境は Linux Python 3.12 であり、3.14 を再実行したとは言わない。異なる圧縮実装一般での ZIP バイト一致も主張しない。

### 初回再構築での不一致観測

初回の再構築コマンドは成功終了し、期待どおりの 3,498,756 bytes / SHA を報告した。しかし後刻の実ファイル検査では、同じ出力先の ZIP が 1,332,779 bytes、SHA `e92205b67ea18c0e14bd85bde2ba54618a8e43b36bfe4d0a2819859d6f45f871` となり、ZIP として開けなかった。sidecar は期待 SHA のままだった。

原因は特定できていない。別出力先への再構築後、実ファイルサイズ・SHA・ZIP 判定・元 ZIP との全バイト比較を行い、すべて一致した。`package-observed.json` に両方の観測を残した。成功ログや sidecar だけを根拠に、最初のファイルまで正常だったことにはしない。

公開用の受渡しでは、既に文書にあるとおり、最終 ZIP 実体を外部の期待 SHA と照合する。今回の観測から新しい理論・認証機構を追加する必要はない。

## 計算資源と公開までの扱い

現在の構成は、前回勧告した「入口は一度受け取り、その状態で操作する」を実現している。要求変更時は許可だけを作り直し、元の差と正規の観測を保持する。異なる不成立要求を経由して戻っても、元値・派生値の追加読出し 0 で再判定できた。

0 は数値読出しの追加回数であり、計画検証・式評価の CPU 費用ではない。保存再開には命令列の再演費用がある。通常操作を保存読込で往復させない、成功命令 64 件・有限三輪の範囲を保つ、という運用は妥当。

本監査も新規 8 テストと限定した追加試験だけを実行した。E1 の 42 テストや全 247 テスト、学習・過去実験の再実行はしていない。初回再構築の不一致に対してのみ、別出力先で追加の一回を実施した。

**この候補を基準として保持し、次は別の AI が手順書だけで操作できるかを確認する段階に進める。** 機能を増やす前に、失敗時の応答と再開手順を含む使いやすさを検査する価値がある。

P0 内の `E2_independent_audit=False` / Linux 未確認は候補作成時点の記録である。本監査を外側に付記できる。候補の内容を更新する場合は別の SHA を持つ新候補として扱い、監査した ZIP の同一性を崩さない。
