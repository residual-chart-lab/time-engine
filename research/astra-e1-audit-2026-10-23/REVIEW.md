# E1 限定入口監査 — Astra

2026-10-23。対象は PR #8、固定版 `0f708c1d35eda52415a24347839d122046cf595b`。
基準 main は `fbf0bb413436f26b29825addccd435aace288fa3`。本監査は実装を変更せず、入口の発行・要求との分離・搬送と保存再開・計算資源を検査した。

## 判定

**PASS — 宣言された RR69 対角 source 族の限定入口仕様として固定してよい。**

確認範囲で、修正必須の欠陥は見つからなかった。任意の外部履歴・任意の要求を扱う一般入口、同一プロセス内の悪意ある Python コードに対する隔離、未来因果一般の証明を認定するものではない。

成果は、確定した差と履歴を搬送し、受信側で正規入口を発行した後、別途与える要求と現在の選択によって三輪を進められることにある。入口の認証は、新しい要求への成立許可を含まない。

## 1. 入口発行

`entry_transport.loads` は、外部で保持した期待 SHA-256 と期待入口 digest、既知型と graph、固定 RR56 入力との対応、実際の閉鎖、S/U の出所と係数、bootstrap 後の全 Engine、数の完全な保存状態を順に照合する。4 層への発行は最後に行われる。

固定入力から再構成した履歴と受信履歴を比較するため、同じ終端値や同じ digest という自己申告だけでは、異なる履歴を入口にできない。実装の比較範囲と、追加の失敗試験は整合している。

追加試験では、外側の SHA を改変後のデータに合わせて再計算した。単なるチェックサム違反だけで落としていない。期待入口 digest は元の値に固定した。

改変項目は、履歴イベント名、上下層の継承値、在庫の削除、両 source の保持差、元の係数、公開 U の値、source の役割交換、履歴の切詰め、数の archive。既存の graph packer で記録化し、読込側の型不変条件または物理履歴・完全値比較で拒否された。各失敗前後で発行 registry の長さが一致した。

期待ハッシュの信頼元は呼出側の責任である。E1 は署名配布サービスや、任意入力の正当性を自動保証する入口ではない。この境界は仕様に明記されている。

## 2. 過去の認証と新しい要求

入口には新しい Scope、選択、Plan、Action を含めない。`start` が要求を束縛し、`choose` が現在の選択を行い、`resolve` が要求に対する判定を行う。

今回、正規に受信した同じ入口で次を確認した。

- chart 外の要求は `UNKNOWN_CHART` / `REJECTED`。実行できない。
- 成立に必要な値を許さない domain は `EMPTY` / `REJECTED`。実行できない。
- 一つの要求で発行した計画を、末輪の接続強度を変えた要求へ流用すると拒否される。

最初の二例では `plant.produce` を例外に差し替え、判定中に要求の実運動を先行実行していないことも確認した。元の Engine は不変だった。

したがって、過去が正規であることと、今回の未来要求を成立させられることは分離されている。C は現在の選択を代行していない。

## 3. 搬送と同じ出来事の再開

公開 E1 記録を Linux の `python -I` で受信した。七つの登録・過去生成器を禁止したまま、在庫 6 の入口から、第一輪完了時の保存・別入口への再開、三輪と上位セルの閉鎖、完了記録の再開まで通過した。過去生成器の呼出しは 0。

受信後の完了記録は 162,897 bytes、SHA-256 は

`5149e8d86856b514c13ea2e9a9c3f8995410d2adef7c917d8439a9ba21479415`

であり、提出済み Windows CPython 3.12.14 / 3.14.3 の記録と一致した。Linux 側で生成して再開した記録と、Windows 記録に報告されたバイト列の同一性が確認できた。

旧 RR69 記録とは、復号後の実状態・在庫・履歴と graph 以外の全項目が一致する。旧 RR69 形式とのバイト一致は主張しない。別プロセスのメモリアドレスではなく、記録された出来事と値・順序の一致を「同じ出来事」の保証範囲とする。

## 4. 計算資源と公開版への勧告

**受入の検証は維持し、検証済み入口・計画・観測を再利用する。** 新しい要求を与えるたびに入口を読み直したり、過去を生成し直したりする必要はない。

追加試験では、同一入口・同一要求・正規のキャッシュを用いた再判定で、元 Vault と派生 Vault の `exact` を禁止しても同じ Action を得た。追加の元値読出し、派生値読出し、新規特徴問い合わせはすべて 0。これは総計算量 0 という意味ではなく、キャッシュの出所・値や計画の恒等式検証は残る。

参考値として一回だけ測定した受入は約 0.798 秒、計画構成は約 0.067 秒。負例検査後の同一プロセス測定であり、一般的な速度保証や比較ベンチマークではない。

公開へ向けた優先順は次で足りる。

1. 今回通った限定 E1 を固定し、任意履歴へ急いで広げない。
2. 次の操作系は、受信済み Entry を保持して Scope / 選択 / 観測 / 一輪ずつの進行を操作する。受信・履歴再演を各操作に挟まない。
3. 正規のキャッシュを再利用する。新しい要求には新しい成立判定を行い、前の許可は流用しない。
4. 現行 checkpoint は再演方式なので、毎操作で保存読込を往復させない。保存は復旧用の段階境界に置き、履歴を削って節約しない。

2 MB / 4,096 nodes は入口のサイズ制限であり、任意の整数・式・長期プロセスに対する CPU / メモリ一定の保証ではない。発行 registry 等もプロセス内に蓄積するため、長時間運用の容量管理は別の課題。今回の有限三輪を連続常時稼働器に広げて評価していない。

## 軽微な文書・報告整備

- `ENTRY_TRANSPORT_E1.md` 末尾は初回時点の「別 Python 環境未確認」のまま。現行の portability 文書と本監査への案内を足すと誤読を避けられる。
- external 検査器の `operating_system_changed` は固定 `false`。Linux で実行してもその値になる。本監査では runtime の実値と Windows の提出記録を比較した。環境比較の根拠を伴う項目へ改めるか、固定値を省くとよい。数学・入口発行の不具合ではない。

これらは限定入口の固定を妨げない。実装を肥大化させず、次の操作系に進む判断を支持する。
