# RR66監査補修 — 既読の関係から一つの読出しを省く

2026-10-22。監査前の固定版は`cb4d505dd1c93bd1b6194593a1225500f0e304e4`。
[Astra監査](https://github.com/residual-chart-lab/time-engine/blob/audit/rr66-astra-2026-10-22/research/astra-rr66-audit-2026-10-22/REVIEW.md)のP2指摘への補修。RR66の模型、要求、作用則、自由数runtimeは変更しない。

**既にp=stとw=as+btを読んでいるなら、個別値へ切り替えるとき、sだけを読み、t=(w-as)/bを求めればよい。** 新規読出しは2回から1回になる。

p,wだけでは一般に二枝が残るので、その段階では個別値を決めない。sを読んだ後に関係式を再利用し、導いたtを元値のcommitmentへ照合する。両語の係数(a,b)=(7,8),(8,7)で検査した。逆にtが既知の場合、あるいは既読の和u=s+tと一方の個別値がある場合にも、もう一方を一意に求める。

これは消した値の再生ではない。元値・関係・由来は保持されており、どこから新規に読んだかと、既読の関係から導いたかを分ける。pと一方の個別値からの除算など、任意の復元方法を探索する最適化は追加していない。有限な線形関係の再利用である。

## 検証

- 適応実行の34テストとRR65の27テスト、計61テストが通過。新しい試験は、両語での一読出し、逆向きの復元、和からの復元、線形観測がない場合、誤った復元値の拒否、tの直接読出しを禁止した実行・保存再開を含む。
- 既存の64計画・11検査群・5つの二輪実行・7時点の保存再開を再現。主出力三つは公開版とバイト単位で一致した。
- 直接の(p,w)→(s,t)移行を両語で追加実行し、二輪と上位セルを認証。準備状態からの再開後も同じ運動になる。
- 元値と派生観測の両アーカイブはA/B比較でも不変。元値を省略した保存には切り替えていない。

現在の検証記録は[repair-validation.json](repair-validation.json)、検査ログは[validation.log](validation.log)。監査前の`integrations/inquiry/RR66-*`の実験結果・検証報告・来歴は履歴として残した。旧検証報告のソースハッシュを現在のソースに対する検証だとは扱わない。

## どこで費用が変わったか

同じ入口、同じ(p,w)キャッシュ、同じ要求更新`mixed/1/1024 → main/1/1024`、同じ語`HHHSUT`、現在係数v=1で比較した。切り替えるのは`derive_cached`だけで、補修前の関数は[reference_derivation.py](reference_derivation.py)に固定した。旧版を実行用の代替経路として組み込んではいない。

一つの環境（Windows、CPython 3.12.14）の3対の測定。順序を前→後、後→前、前→後と交互にした。登録と計画は変更されないため共通に測り、計画のキャッシュを消した場合と、直後の再利用を分けた。以下は中央値、単位ms。原データと環境・測定条件は[cost.json](cost.json)。

| 段階 | 補修前 | 補修後 | 解釈 |
|---|---:|---:|---|
| 登録 | 共通：1500.6 | 共通 | 過去の認証済み入口と6観測の用意を含む。今回の削減対象ではない |
| 計画、計画キャッシュを消した場合 | 共通：98.26 | 共通 | 多項式の証明を作る費用 |
| 同じ計画の再利用 | 共通：0.0648 | 共通 | 既存の計画キャッシュ。今回新たに得た高速化ではない |
| 精査・作用の準備 | 71.65 | 71.46 | 新規読出し2→1、復元0→1 |
| 二輪の実行・認証 | 1764.05 | 1757.91 | 物理作用と成立結果は同じ |
| 完了記録の保存 | 1904.10 | 1881.43 | 完全なコマンド・運動の再演を含む |
| 完了記録の読込 | 3731.90 | 3723.04 | 数アーカイブと履歴・実運動の再検証を含む |

**読出しは減ったが、今回の測定から全体の高速化は主張できない。** 精査の測定範囲は重なり、実行・保存再開もほぼ同じ規模である。今のVaultの`exact`はメモリ内の値の参照であり、関係式の有理数計算とcommitment照合は残る。初回のp,wの2読出しも含めると、この要求列の新規読出しは合計4→3である。

完全な保存・読込の再認証に費用がかかっているが、今回その保証を弱める変更はしていない。保持参照数も6のまま。完了記録の2バイトの差は読出し履歴の表記によるもので、保持量圧縮の成果には数えない。測定した段階の和を、任意の運用での所要時間や一般的な速度向上率にしない。

## 履歴の版境界

今回変更した移行の古い記録には、s,tを両方読んだ履歴がある。新しい実装で黙って「sを読みtを導いた」へ変更して受理しない。旧履歴は旧版の固定コミットで再演する。[replay-boundary.json](replay-boundary.json)に、この境界の確認を保存した。公開済みの三つの主出力はこの移行を含まないため、補修後も同じバイトを生成し、保存記録も再演できる。

## 再現

リポジトリのルートで、Python 3.10以降、標準ライブラリのみ。

```sh
python research/rr66-read-repair-v001/validate_repair.py
python research/rr66-read-repair-v001/check_replay_boundary.py
python research/rr66-read-repair-v001/profile_repair.py --samples 3
```

新しい出力は`.work/rr66-read-repair/`へ置き、ここに固定した測定値や旧版の実験結果は上書きしない。費用の測定値は環境や負荷で変わる。合否条件にするのは厳密な作用・キャッシュ・保持アーカイブの一致と、読出しの2→1である。
