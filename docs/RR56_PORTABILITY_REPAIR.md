# RR56補修 — 記録の搬送と、実験の再現を分ける

2026-10-17。Astraによる[初版d7a8387の監査](https://github.com/residual-chart-lab/time-engine/commit/d7a8387ec26fc2b06b454337063f2336e418a686)で、主9群・68テストと往路の成立は再現した一方、上流の浮動小数の微小差により、配布済みの記録の読込が拒否された。[提供された監査原文](../integrations/three_plus_one/astra-audit-user-supplied.md)を保存する。

**往路の演算・校正・未来要求は変更しない。原記録のSHA-256に束縛して、その値と履歴をそのまま搬送し、受け渡しとTE側の有理数計算を検証する読込経路を加えた。既存の「この環境で上流から完全に再現する」経路も残す。**

## 1. 旧読込で何が起きたか

初版の`import_occurrence`は、JSONの復元後に3+1の基準学習を最初から実行し、現在位相、保持差、応答行列、source、接触後の基準ネットワークまでローカルな値と完全一致することを求めていた。

Python・数学ライブラリ等の違いによって上流のbinary64値が僅かに異なれば、保持一候補／消去四候補という判断が同じでも、記録全体は一致しない。そのため、**別環境ではバイト不一致だけでなく、配布済み記録の読込自体が失敗し得た。** 現在も、再現モードでの完全一致を全環境へ保証するものではない。

この差を許容誤差で同じ履歴へ寄せる修正は行わない。固定要求F、ε=10⁻¹²、保存された実際の終点と17パラメータ、接空間の履歴は保つ。

## 2. 二つの検証方法

| 検証 | `reproduce`（既定） | `transport`（明示して使用） |
|---|---|---|
| 入口 | 元のJSONまたはそのbytes、期待する設定とC | 元ファイルのbytes、外から信頼したSHA-256、期待する設定とC |
| 上流の学習・J・K | 使用環境で再計算し、完全一致を要求 | 保存された有限値を、認証元が明確な入力として受け取る |
| 保持差・位相・応答の形 | 再計算したものへ照合 | 保存値の上でexactな分解と射影を再検証 |
| 四候補・固定C・現在の自由選択 | 正規のローカル生成と照合 | 保存された同じ写像を有理数で再検証 |
| TE source実行・認証・公開、一輪の閉鎖 | 再実行して照合 | 同じ保存係数から有理数で再実行して照合 |
| 保存された神経接触後の値 | ローカルな更新と完全照合 | 原記録のハッシュへ束縛。独立したSGD再計算としては検証しない |
| 全履歴・実際の終点 | 保存値を変更しない | 保存値を変更しない |

搬送は、**元の実験が正しかったという独立な再実験の代替ではない。** 信頼した固定版の記録を受け取り、そこから先の写像とTEの計算を再検証する手段である。出所の検証と、元の浮動小数の力学を独立に再検算することを分ける。

## 3. 公開済み三記録を読み込む

```text
python integrations/three_plus_one/validate.py --transport-only
```

`records/manifest.json`の設定・C・自由選択値と、初版から不変の三ファイルのSHA-256を用いる。このコマンドは3+1の基準学習、J、K、sourceの根を解き直さない。結果は`upstream_floating_point_regenerated: false`、`independent_upstream_dynamics_verified: false`と表示し、exactな受け渡しとTE再認証の成功を別に示す。

マニフェストは信頼した固定コミットから取得する。記録とハッシュの両方を未確認の同じ相手から受け取っただけでは、信頼基点にはならない。SHA-256は作者の署名でもない。

APIでは、`import_occurrence`へ`verification='transport'`と`trusted_sha256`を明示し、元ファイルを`read_bytes()`した値を渡す。dictからの搬送読込は許さない。期待するCもマニフェストの正確な有理数から読む。特に別の未来fixtureをローカルな3+1値から作り直すと、原記録と違うCになる可能性がある。

`verification`を省略すると従来のローカル再現である。違いを検出すると`LocalReproductionMismatch`を返し、環境差またはデータ差である可能性を明示する。自動で搬送モードへ切り替えることはない。未知型・循環参照・固定要求・誤差基準・入口・介入・選択値の照合も維持する。

## 4. 共有された不変構造も保持する

旧デコーダでは、許可されたdataclassの正規化処理が、値の等しいtupleを作り直すことがあった。数値と入れ子の内容が同じでも、再出力時の参照番号が変わり、元のJSONグラフとバイト一致しなくなる。

補修後は、各コンストラクタの検証と正規化を通常どおり実行する。その結果が元のフィールドと同じ型・同じ値であることを確認してから、元の不変値の参照を戻す。検証を迂回せず、保存された共有関係も復元する。初版の三記録について、読込→再出力が元のbytesに一致することを検査した。

## 5. 検証したことと、未確認の範囲

新10検査を追加した。上流スナップショットを`nextafter`で1 ulpずらす対照では、許容候補は保持一／消去四のまま、再現モードは不一致を検出する。搬送モードは元の記録を元のbytesへ復元できる。

さらに、上流学習・J・K・ローカル入口生成・根解法を呼ぶと失敗するよう禁止した状態でも、公開済み三記録の搬送が通る。固定C、入口、介入、選択値の差し替え、原SHAからの1バイトの変更、未知型、循環参照、TE終点・射影の偽造を拒否する検査も残す。

補修版の主9群と、既存68＋新10＝78テストを実行する。保存物と数値の比較結果は`RR56-portability-validation.json`へ記録する。初版の`outbound_result.json`、`RR56-driver-validation.json`、`RR56-validation.json`、`RR56-PROVENANCE.json`はd7a8387の履歴として保持し、補修版の根拠と区別する。

今回の追加検査は、この環境での1 ulp差の模擬と、浮動小数の再生成を禁止した経路の検査である。Astra側の別環境で補修版を再実行した結果を受け取った、とは記載しない。TEと写像のexact検証は行うが、上流SGDの環境間での完全再現を新たに保証しない。

## 6. 数値再実行で原記録を上書きしない

```text
python integrations/three_plus_one/validate.py
```

この環境の数値結果・実行時間・新しく生成した記録は、`.work/rr56-local/`へ書く。公開済み`records/`の三記録とマニフェスト、初版の検証記録は上書きしない。`outbound.py`を直接実行した場合の主結果も、同じ作業用ディレクトリへ出力する。

部品や学習則、接続写像、未来要求を増やした補修ではない。往路の成果を維持して、記録を運ぶ工程の保証範囲を明確にした。復路へ進む前の補修はこの範囲で完了に置く。
