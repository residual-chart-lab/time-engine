# 状態は記録ごと渡す

**表示値が同じでも、状態まで同じとは限らない。状態は記録ごと渡す。**

Time Engineを操作するために、自由数の実装や理論を先に学ぶ必要はない。次の三つを守れば、用意された入口と要求の範囲で使える。

1. 続きを渡すときは、`save`で作った記録をそのまま渡す。返されたSHA-256も別に保持し、同じ入口とともに再開する。
2. 要求を変えたら、`bind` → `choose` → `resolve`で判定し直す。再利用できる観測は内部で再利用される。変更できるのは第一輪を実行する前まで。
3. 表示値や`status`を、新しい保持状態の代わりにしない。数値を外で計算に使うことと、その数値から元の状態を引き継ぐことは別である。

## 受け取るものの違い

| 受け取るもの | 用途 | 続きの実行に必要な状態を運べるか |
|---|---|---|
| `status`や数値の表示 | 現在の段階・判定・費用などを読む | その表示だけでは運べない |
| 認証済み入口の記録 | 固定された履歴と保持差を受け取る | 対応する入口検証を経て受け取る |
| `save`で作るセッション記録 | 要求・選択・観測・実履歴を含めて保存する | 同じ入口と外部のSHA-256を指定し、検証して再開する |

入口のdigestは入口の識別子であり、進行したセッション全体の識別子ではない。`certified`などの表示を書き写すだけで認証を引き継ぐこともできない。

## 自由数が内側で守ること

ある要求では、保持差を詳しく展開しなくても十分な読み方がある。別の要求では、同じ保持差の精査が必要になる。省略できると分かった演算は省き、元の差は保持する。省略の保証は、その要求と演算範囲に限られる。

したがって、「同じ読出し値だった」という事実だけでは、任意の後続で二つの状態を置き換えてよいとは決まらない。これは通常の数学で同値類を使うことへの否定ではない。どの作用について同一視してよいかという範囲を明示する、という扱いである。

通常の操作では、この判定を利用者に委ねない。状態と対応する要求を渡せば、既知の運動式・認証範囲・有限予算の中で必要な読み方を構成する。任意の新しい数や自然言語の要求を処理できる一般入口ではない。

## 実装や接続則を変えるAIへ

読出し値だけをキーに状態を統合したり、現在の要求で不要だった差を記録から削ったりする変更には、この区別が必要になる。内部の観測キャッシュにも、値だけでなく元の保持状態・観測定義との対応がある。

変更する場合は、**元の差を保持すること、置換可能性の範囲を限定すること、要求が変わったら成立許可を取り直すこと**を保つ。

## 次候補E3の具体的な境界

E3の`status`には`schema: time-engine-session-view-v1`が付く。返答中の要求や費用情報は内部から切り離したコピーなので、呼出し側で編集してもセッションには反映されない。これは通常のPython APIの返答についての境界であり、同じプロセス内の任意のコードへの隔離機構ではない。

表示のschemaは再開記録のschemaと異なる。表示や値だけの要約を、入口や再開記録の代わりに渡しても受理されない。セッション記録の形式は従来どおりで、P0で作った保存記録も検証して再開できる。

このE3の補強は次候補用であり、固定済みP0 ZIPの内容は変えていない。P0の通常操作でも、上の三つの扱いは同じ。起動と保存再開の手順は[P0起動案内](P0_STARTUP.md)、E3の判定表示は[E3の説明](E3_DECISION_FEEDBACK.md)を参照する。
